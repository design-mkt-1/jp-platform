Section 13 is the comparison itself: twenty-six Figma / implementation comparisons, plus an accessibility sheet. Section 14 is what came out of looking at the site in Chrome on 9 September: five defects found and fixed, with the after screenshot next to the Figma node.

02

What we actually checked

A green dot means measured: we ran the query and read the result. An amber dot means we still don't know, and we're not guessing.

Figma has no design tokens

Querying the variables on desktop-main returns a single value, BG/Quaternary: #0D1420. On UI Kit — Desktop it returns nothing. All the colors are fills hardcoded into layers. In plain terms: if the designer changes the card background tomorrow, the change doesn't propagate anywhere on its own — it has to be read again.

The UI Kit, on the other hand, is written like documentation

The Colors frame has five groups, and every swatch already carries a semantic name: Page Background, Card Background, Blue Primary, Gold Nav Active. Those names become the Tailwind token names directly, so the mapping isn't something we invented, it's transcription. The full palette is below, in section 03.

The fonts are all open-source

Inter, Roboto Flex, Bricolage Grotesque. All three are Google Fonts, so they load through next/font/google with no license to buy and no files to host.

The two "mob main" screens are not a duplicate

We compared the two subtrees line by line. Out of 894 lines of structure, exactly one thing differs: the header. 1:6978 has Header (Pre-login) with two Sign In buttons, while 1:5720 has Header (POST-login) with the green balance button and a plus. The rest is identical. So mobile doesn't have two pages, it has one page with two headers — exactly like desktop, and the mobile work doesn't double.

The design has no distinct image per game

PopularGames and CrashGames both contain the same six "Gates of Olympus 1000 / Pragmatic Play" cards. The provider row has five unique logos repeated to fill sixteen slots. Concretely: if I simply download what's in Figma, I get one game image, not sixty — and a demo where every game looks the same reads as a defect, not as design.

I don't know yet what shape the asset export takes

I haven't run the download yet. I don't know whether the provider logos come out as SVG or PNG, at what resolution, or whether the file names collide with each other. That's why the assets phase is sequential and kept separate: if it comes out badly, redoing it is cheap and it blocks nobody.

03

The design system, pulled out of the UI Kit

The colors below are read out of the Colors frame in the Desktop UI Kit, not picked by me. The page you're reading right now is painted with exactly these values — that's the first check that the palette holds. They become tailwind.config.ts, the single source of truth for colors in the project.

What a token is

A name given to a color, used instead of the value

A design token is quite simply a name. Instead of writing the color #151624 in the code, you write bg-card. The name means "the card background", and somewhere, in a single file, it is written down once that bg-card means #151624.

The concrete example from this project. The Gates of Olympus 1000 game card in the Popular row sits on the #151624 background. Exactly the same color is on the card in Crash Games, the card in Must Play Slots, the Balance panel that opens from the header, the jackpot menu on mobile and every block in the footer. That's a few dozen places.

Without a token

The color is written by hand in every component. Tomorrow the designer says "the cards are too dark, make them #1A1B2B". You have to find every occurrence and change them one by one. A few will be missed — and they'll be missed exactly in the places nobody opens often, meaning the search with no results state or the VIP menu.

With a token

All those places write bg-card. The change is one line, in tailwind.config.ts. There is no "I forgot one", because there are no copies — there is one definition and dozens of references to it.

Where risk R-2 comes in. Normally those names live inside Figma itself, as variables, and the code can read them automatically. Here they don't — we checked, the file has a single variable. What we have instead is the UI Kit, where the designer wrote the names as text under each color square: Page Background, Card Background, Gold Nav Active. So the names exist and they're good, but the link between Figma and code is a document we write ourselves (docs/tokens.md), not something that syncs on its own. If that document turns out sloppy, the agents building the components start writing colors by hand again — and we're back to exactly the left-hand column.

05

How the design gets into code

One single direction of flow. Every box has a single owner, and everything to the right of a box only reads from it, never rewrites it.

The part that matters: the registry in the middle. Everything that describes a screen lives there as data. That is why a new screen from the designer touches neither the page, nor the tokens, nor the existing components.

06

The main decision: 12 rows become data, not code

Of the 15 content rows on desktop, 12 are exactly the same pattern: a header with an icon, a title and a “See All” link, followed by a grid of cards. Only the title and which games go in the grid change.

The naive version

12 hand-written components

Every row, its own file. When the designer asks for the section titles to be 2px bigger, it changes in twelve places. When they add a new row, you write a thirteenth, almost identical component. 

// 12 almost identical files

NewGames.tsx
CrashGames.tsx

… eight more …
The version we chose

One component + one registry

A single ContentRow, fed by a list of descriptions. A new row means four lines of data. A style change happens once, in one place. 

// src/lib/sections.ts
{ kind: 'games', id: 'crash',
  title: 'Crash Games', grids: 1,
  filter: { tag: 'crash' },
  figmaNodeId: '1:3230' }

The figmaNodeId field is not decoration. It is what turns the visual check from a chore of twenty manual comparisons into an automatic loop: for every entry in the registry, take the Figma screenshot, take the browser screenshot, put them side by side.

The three big banners

Tournament, Lottery and Wheel are all 1280×260 and share the same anatomy. One component, three variants.

Application state

A single Zustand store holds the sign-in mode, the search state and which panel is open. No provider, so the rest of the page stays server-rendered.

The data

60 games in JSON, re-sliced into rows by filters. The “See All (206)” label stays exactly as in the design, without us inventing 206 records with broken images.

07

Orchestration: a sequential spine, then a fan-out

Eight agents cannot write the same shared components in parallel. The answer is not isolating them in separate copies of the repo, it is splitting ownership by file: each agent gets the exact list of files it is allowed to create and the list of the ones it is only allowed to read. The sets do not overlap, so there is nothing to reconcile at the end.

Decided in review: the eight do not all start at once, they go in two waves of four. Wave one takes Header, Hero, Rows and Footer — the areas that touch the most primitives. If something comes out wrong there in the game card or the button, it gets fixed once, not eight times.

Why phases 1–3 cannot run in parallel: the tokens and the primitives are the shared vocabulary. Two agents reading the UI Kit on their own will christen the same gray bg-surface once and bg-card the next time; two agents writing the game card produce two different game cards. Serializing the foundation is exactly what keeps the fan-out of eight free of conflicts.

Who owns what, in phase 4

They all import from the tokens, types, store and primitives. None of them modifies any of it.

Technical decision

We do not use isolated copies of the repo

It looks like the safe choice for eight parallel agents, but here it does damage. Every copy would need its own dependency install — eight installs of a few hundred megabytes each, before anyone writes a single line. And with no dependencies installed, an agent cannot even run the type check, which means it loses exactly the control that justifies working in parallel. Splitting ownership by file already solves the collisions, so isolation would pay a steep price for a problem that does not exist.

08

When the designer adds screens

You said more screens are coming. The architecture is built around that assumption, not bent to fit it afterwards.

  1. A new games row — you add four lines to the registry. Zero new components, zero files touched. Five minutes.
  2. A new standalone screen — one entry in the screen registry, with the Figma node and the viewport, plus a component assembled from primitives that already exist.
  3. Verification happens by itself — the internal /dev/screens page automatically renders any entry in the registry, with the Figma node attached, so the comparison loop picks it up without any change at all.

Here is what makes the difference: a new screen never touches the colour configuration, the state store, the app layout or the existing components. If they ever do have to be touched, it means the designer has introduced something genuinely new — and then it deserves a conversation, not an improvisation.

09

How we prove it looks like the design

Five gates, from the cheapest to the slowest.

  1. Type checking and lint, after every agent. It writes nothing to disk, so it can run in parallel with no risk.
  2. Colour discipline — a lint rule rejects any hex code written straight into a component. If someone writes #151624 instead of using the token, it fails at lint, not at human review.
  3. Full build and starting the server, in the sequential phases only. Zero errors in the console, zero hydration warnings.
  4. Visual comparison per section — for every entry in the registry: the Figma capture, then the browser at 1440 or 390 pixels, then the real screenshot, placed side by side. The deviations turn into fixes in the files owned by the agent for that area.
  5. Interaction test — switching prelogin → postlogin → VIP; typing zeu for suggestions, xyzzy for the no-results state, clearing the field for the initial state; opening and closing both panels; all three jackpot menus at 390 pixels.

Five things that can wreck the execution. The first one is the most likely and it blocks everything, so it gets checked before any agent starts.

12

The checks before phase 0 — results

The five risks, actually checked. Each one has a verdict and the evidence for it. Two of them came out differently from what the plan said — I have flagged those explicitly.

R-1 · Handled

The scaffold really does refuse the directory — and the move had a flaw

I created a test directory with .claude and .git inside it and ran the command. It refuses, exactly as suspected. .git passes, .claude does not: 

The directory r1-probe contains files that could conflict:

  .claude/

Either try using a new directory name, or remove the files listed above.

What I had not anticipated: the move from the sibling directory fails too, because create-next-app creates its own .git in the scaffold, and you cannot write over the existing .git: 

Move-Item : Cannot create a file when that file already exists.
  (C:\...\r1-scaffold\.git:DirectoryInfo) [Move-Item], IOException

The corrected procedure — you delete the scaffold's .git first, then move — has been tested and it passes: the final directory contains .claude intact, the original .git intact, plus everything Next generated.

R-2 · Handled, but it needs a decision

The two UI Kits contradict each other on the same names

I read the Mobile UI Kit as well, not just the Desktop one. Five names appear in both, with different values. They are not mistakes — they are different decisions for different screens. But it means that a single token table cannot have a single value for each name.

Name in FigmaDesktop 1440pxMobile 390px
Page Background#11111A#0F121D
Overlay#000000 @ 20%#161625 @ 80%
Secondary Text#FFFFFF @ 70%#FFFFFF @ 60%
Blue Tinted BG#007AFF @ 13%#007AFF @ 15%
Card Border#FFFFFF @ 4%#262632

On top of that, mobile brings in four colours that do not exist on desktop — Section Background #12162B, Caption Text #8E9BB0, Emerald Green #00F299, Cyan Accent #00F0FF — and it names the same value differently: desktop says Separator, mobile says Divider, both of them #282936.

The complete table is written: 26 desktop colours, 22 mobile ones, 30 distinct tokens after unification, 5 of which have two values.

Decided

The values from the Mobile kit win

One value per token, the mobile one, applied to both viewports. The decision applies only to the five names in conflict; the tokens that exist only in the Desktop kit — Gold Nav Active, Nav Inactive, Footer Heading and the rest — keep their values, otherwise the active pill in the category bar would lose its gold.

One single exception, added after the visual check: bg-overlay keeps both values, switched at 768px. Here the kits differ for a reason, not out of carelessness — on desktop the layer sits behind a small panel in the corner and leaves the page readable at 20%, on mobile behind a sheet that covers the whole screen, at 80%. With a single value, the Balance panel on desktop came out much darker than in node 1:4116.

R-3 · Handled, the plan changes

The asset export cannot be done on whole rows

I ran the download on four different nodes. The results:

  • On the whole provider row — out come more than 20 SVG files, cut off at 20, with a truncation message and no names. They are layer fragments, not logos: one of them is literally a black rectangle, <path d="M59 0H0V10.2924H59V0Z" fill="black"/>, that is, the logo's mask.
  • On a single logo — clean: two SVGs, the 286-byte mask and the real logo at 6233. Plus a PNG export of the whole badge, 4.4 KB, which looks exactly like the design.
  • On the hero banner — four raster images, correctly PNG. But the big one is 4096×1360 px, 5.7 MB. For a demo it has to be resized, otherwise the page's first load pulls six megabytes on its own.
  • On the game card — the surprise: the game art exists as an animated GIF 480×640, 2.7 MB, plus a static PNG variant 240×320, 125 KB. The design has animated cards.

What changes in the plan: the assets phase does not download by rows, but node by node, and it takes its file names from the Figma layer names. The providers are already named there — Badge-Pragmatic, Badge-3 Oaks, Badge-BGaming, Badge-Nolimit, Badge-Spribe — so there are five providers, not sixteen.

Decided

Static PNG only, no animation

The game art exists in Figma as an animated GIF of 480×640 and 2.7 MB, plus a static PNG variant of 240×320 and 125 KB. Only the static one gets used. With sixty cards on the page, the animated version would have meant hundreds of megabytes on a single load.

R-4 · Handled

The placeholders, next to the real card

The first one is the card exported from Figma, at its real size, 203×264. The next three are the proposed placeholders, at the same size. Worth noting: in Figma the card has no text node — the title and the provider name are baked into the image. So the placeholder has to draw them itself.

Incident, fixed structurally

The site returned 500 on every route, even though the code was correct

During the check, the server started returning Internal Server Error on any address. The code compiled without a single error. From the server log: ENOENT ... _buildManifest.js.tmp.z5fzbd71okj. The cause: I ran a production build while the development server was running, and both write into the same .next directory. They stepped on each other and corrupted the manifest.

That prohibition was written into every agent's prompt. The one who broke it was the parent, which is me. That is why the fix is not a reminder note: next.config.ts now reads NEXT_DIST_DIR, and npm run build:check sends the build into a separate directory. Verified: full build run, the server stayed on its feet.
