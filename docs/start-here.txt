WHAT YOU NEED ON A NEW MACHINE
------------------------------

- Node 24
- Git
- Google Chrome

Chrome is required, not optional. The capture scripts drive the browser already
installed on the machine (channel: 'chrome'), not one downloaded by Playwright —
that download fails in this environment. So `npx playwright install` is NOT
needed, only Chrome.


GETTING STARTED
---------------

    git clone https://github.com/design-mkt-1/jp-platform.git
    cd jp-platform
    npm ci
    npm run plugins
    npm run dev

Then open http://localhost:3000

Tested: a clean clone plus npm ci plus a full build all pass. 172 files.

WHAT DOES NOT TRAVEL WITH THE REPO
----------------------------------

This is the part you cannot infer from the code.

Your working rules are LOCAL configuration, not repo configuration. The two
rules that show up on every message — "do not assume, verify" and "explain, do
not just report" — come from:

    <your home>/.claude/settings.json     (the "hooks" section)
    <your home>/.claude/CLAUDE.md

The same goes for caveman mode and the installed skills.

On another machine, without them, Claude will produce dry reports and fill gaps
with plausible guesses instead of asking — exactly the behaviour those rules
block. If you want the same working style, copy those two files across.

What DOES travel with the repo, as of 2026-09-09: .claude/skills/ (20 skills,
committed), CLAUDE.md at the root, and .claude/hooks/skill-triggers.mjs — a
UserPromptSubmit hook wired in .claude/settings.json that injects the skill
triggers on every turn. That hook exists because the passive version failed:
ui-ux-pro-max was enabled from the first commit and one whole session still ran
a 49-control UI audit without invoking it once.

The plugins themselves do NOT travel. .claude/settings.json DECLARES them; their
code lives in ~/.claude/plugins/ on the machine that installed them. Declaring is
not installing: installs are recorded per project, keyed by the project's path,
so a plugin installed for another checkout on the same machine still does not
load here.

Do not check this by eye and do not trust `claude plugin list`. Its "enabled"
column is machine-wide — on 2026-09-10 it reported fifteen plugins as enabled
while exactly one of them was installed for this checkout. Run:

    npm run plugins            says what is actually installed here
    npm run plugins:install    installs whatever is missing

Then RESTART the session. Plugins resolve at session start, so nothing installed
mid-session is live in that session. After installing, run
`git diff .claude/settings.json` — the installer rewrites that committed file.

You do not need to know which plugins those are. The list lives in
.claude/settings.json and the script reads it from there. Writing the names into
a document is what produced four checklists that disagreed with each other.

Orca's state is per machine too, and parallel work on this repo runs as Orca
workers with one git worktree each — see the Orchestration section of CLAUDE.md
for why. `orca status` should answer runtimeState: ready. Verified command
surface, so you do not rediscover it:

    orca repo list                       this repo is registered as D:/jp-platform
    orca worktree ps                     what is running now
    orca orchestration run-create --objective ...
    orca orchestration task-create --spec --task-title --display-name
    orca orchestration task-update --id --status

`--task` is NOT a flag, and `in_progress` is NOT a valid status. The set is:
pending, ready, dispatched, completed, failed, blocked.

UNKNOWN: I do not know whether the Figma MCP connection works automatically on
another machine. It is tied to the claude.ai account, so probably yes, but there
is no way to check from here. Quick test in the first session: ask it to run
get_metadata on file 2MyylxdZblfGnf05nQacUz. If it answers with the "Platform"
page, you are fine. If not, the Figma connector needs reconnecting.


THE TRAP THAT COSTS YOU AN HOUR IF YOU DO NOT KNOW IT
-----------------------------------------------------

Do NOT run `npm run build` while `next dev` is running.

Both own the same .next directory. When they tread on each other they corrupt
it, and EVERY route starts returning 500 with:

    ENOENT: no such file or directory, open
    .next\static\development\_buildManifest.js.tmp.<random characters>

The code is perfectly valid. It looks like an application bug and it is not.
This happened exactly that way once, in an earlier session.

That is what this exists for:

    npm run build:check

which sends the build to .next-build and cannot touch the running server.

The accessibility run is NOT exempt, even though it points at .next-a11y for
exactly this reason, and on 2026-09-10 it took every route to 500. The cause is
no longer a mystery. With .next deleted first and no dev server running:

    GITHUB_PAGES=true NEXT_DIST_DIR=.next-a11y next build
        -> .next-a11y 187 files AND .next 239 files, a whole second build
    NEXT_DIST_DIR=.next-probe next build          (no GITHUB_PAGES)
        -> .next-probe 238 files, .next never created

distDir works. The `isPages` branch of next.config.ts, the one that turns on
`output: 'export'`, is what writes into .next anyway. So `npm run build:check`
genuinely is safe while the dev server is up — that is the second line, measured
— and the accessibility run genuinely is not. Stop the dev server before it.

The same thing happens after you edit next.config.ts while dev is running: Next
restarts itself when the config changes and treads on itself. After any change
there, stop and restart the server by hand.
